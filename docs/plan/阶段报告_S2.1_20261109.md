# S2.1 阶段报告：修复预检上传失败，加可选 Google Drive（2026-11-09）

分支：`stage2.1/drive-persistence`（基于 master `cd80a71`）。决策见 [决策记录](决策记录.md) D28–D32。
本阶段只在 CPU 沙箱里用 stub `colab` CLI 和 stub `rclone` 验证过；真实 Colab 上的表现要等你重跑 `preflight`。

## 一、首次预检为什么失败

你发来的日志（运行 `preflight-20261109T014903Z-9e57`，提交 `cd80a7117418`）：

| 时间点 | 现象 |
|---|---|
| 分配 VM | 约 3 分钟，成功 |
| 上传 1/6–3/6 | 成功，分别约 43、30、5 秒 |
| 上传 4/6 `p3_private_082210c90d5b3834.tar.gz.part001` | 连续 3 次失败，每次约 2.5 分钟后报错 |
| 结束 | `ERROR: upload of … failed`，VM 已释放 |

S2 的上传顺序是代码分片、数据分片、`request.json`，分片大小 8 MiB：代码包 12.7 MB 分 2 片，
数据包 21,164,679 字节分 3 片，共 6 次上传，所以 4/6 是数据包的第 2 个 8 MiB 分片。

原因（推断，见下面的限制）：colab-cli 0.7.5 的 `upload` 把整个文件 base64 编码后放进一个 JSON 请求，
经 Colab 运行时代理用一次 PUT 发出（`colab_cli/contents.py`），客户端不设超时。8 MiB 分片对应约 11 MB 的请求体。
3 次失败都停在约 150 秒，符合代理或服务端的时间上限；前 3 片的用时从 5 秒到 43 秒不等，说明上行速度波动很大。

限制：S2 的运行器把 CLI 输出丢进了 `/dev/null`，所以拿不到具体的 HTTP 状态码。本阶段起每次尝试的输出都会保存。

## 二、改了什么

| 问题 | 改动 | 位置 |
|---|---|---|
| 请求体太大 | 上传和结果下载都按 2 MiB 分片（约 2.8 MB 请求体）；`P3_PART_MB` 可再调小 | `scripts/colab/common.py`、`local_tools.py`、`runner.py` |
| CLI 不设超时 | 每次 CLI 调用都有墙钟上限：上传/下载 600 秒（`P3_UPLOAD_TIMEOUT`），引导 4 小时多一点，任务 24 小时多一点；用 `timeout --foreground`，Ctrl-C 照常可用 | `colab/launch.sh` 的 `colab_t` |
| 重试太少、报错丢失 | 每片最多 6 次，间隔 10/20/30/60/60 秒；每次尝试的退出码、用时和 CLI 原文写进 `upload.log`，终端显示最后两行 | `upload_part` |
| “报成功但没传完”无从发现 | 传完后在 VM 上列出每片的大小与 SHA256，和本地比对，只补传缺失或不一致的分片，最多 3 轮 | `colab/kernel_inbox.py`、`verify_inbox`、`local_tools inbox-diff` |
| 每次都要上传 12.7 MB 代码 | 提交已推到 GitHub 时，VM 自己从 codeload 下载这个提交的源码包，按 `git ls-tree` 清单逐文件比对 blob SHA-1；不一致或下载失败就自动改为上传代码 | `colab/kernel_bootstrap.py`、`commit_is_published` |
| 公开结果分支可能泄露 token | CLI 报错里的请求网址带 `colab-runtime-proxy-token`。推送前对文本文件脱敏，记录在 `_local/REDACTIONS.txt` | `local_tools redact`、`push_results` |
| 运行中切换分支会改变 VM 执行的脚本 | 每次运行开始时把 `colab/kernel_*.py` 复制到 `.colab_runs/<run_id>/kernel/`，之后只执行这份副本 | `cmd_run` |
| 引导重试时旧日志干扰判断 | 每次引导尝试单独记日志，只按本次尝试的标记判断 | `run_bootstrap` |

这样一次预检从本机上传的只有约 21 MB 私有数据（11 个 2 MiB 分片加 `request.json`）。
上行速度低到 20 KB/s 时，单片也能在 150 秒内传完。

## 三、可选的 Google Drive

按你说的方式设计：Drive 用 rclone 挂在 `/content/mydrive`，远端名 `mydrive:`。

- 写入一律用 `rclone copy`，再用 `rclone check --one-way` 核对，通过才算保存。不经挂载点写入，因为挂载写入是异步的。
- 只写 `mydrive:ColabProjects/vlm-perception-reward-rl/` 之下：预检结束时把结果包和 `package.json` 复制到
  `runs/<run_id>/`；探针用 `_p3_probe/<run_id>/`，只删除它自己写的文件。
- 运行器不知道你怎么给新 VM 挂载 Drive，所以留了两个入口：本机命令 `P3_DRIVE_MOUNT_CMD`（`{session}` 换成会话名），
  或在 VM 上执行的笔记本单元格文件 `P3_DRIVE_SETUP_FILE`。它们的输出只留在本机，不推到 GitHub；运行器不复制任何凭据。
- 如果挂载进程用的是非默认的 rclone 配置文件（`rclone mount ... --config X`），会自动沿用。
- 新命令 `bash colab/launch.sh drive-check`：在 CPU VM 上写 16 MB 随机文件，读回比对 MD5，跑 `rclone check`，然后删除，
  并测量上传和下载速度。有挂载点时，还会测经挂载写入的文件多久后出现在远端。
- Drive 出问题不会让任何运行失败；正式记录仍是 GitHub 的 `results/<run_id>` 分支。S4 训练时用它多存一份 adapter 和 checkpoint。

设置方法见 [colab/README.md](../../colab/README.md) 第七节。

## 五、还没有验证的

- 真实 Colab 上 2 MiB 分片的上传成功率与速度：要看下一次预检的 `_local/upload_times.tsv` 和 `upload.log`。
- Colab VM 能否访问 `codeload.github.com`（预期可以；不行时会自动改为上传代码，日志里会写明）。
- 你实际的 Drive 挂载方式：需要你配置两个入口之一，再跑 `drive-check`。
- 本机没有 coreutils `timeout` 时（例如未装 coreutils 的 macOS）没有单次调用时间上限，只剩重试和远端核对。WSL2 自带 `timeout`。
