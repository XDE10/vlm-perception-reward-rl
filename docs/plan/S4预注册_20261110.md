## 6. 奖励

每条补全的总奖励：R = 1.0 · R_answer + 0.05 · R_format + λ · R_perception。

- **R_answer ∈ {0, 1}**：只看唯一的 `<answer>` 段。先去掉表述形式（`x = 4` 取等号右边，去掉末尾单位与度数符号、`$…$`、`\approx`），
  再用项目原有的 math_verify 严格类型判定与标准答案比较，不加数值容差（D3、D4、D13）。判定在常驻进程池中运行，单条超时 10 秒记 0 分。
- **R_format ∈ {0, 1}**：perception、think、answer 各恰好一段，顺序正确，段内没有嵌套标签，answer 非空；perception 中至少 1 条可解析的事实，
  原始条数不超过 24。
- **R_perception**：
  - `rl_ans`、`rl_blind`：λ = 0，不计。
  - `rl_v4`：冻结的 `scoped_score`，即只在认证范围内计算的 F1，取值 [0, 1]，λ = 0.2。
  - `rl_v5`、`rl_v5_placebo`、`rl_v5_groupnorm`：v5.1，λ = 0.1。每条去重后的断言判为 TRUE（属于认证正事实）、FALSE（无法解析，
    属于认证负事实，与认证常量冲突，或被 InterGPS 几何证伪）或 UNKNOWN（其余）。

    R_v5 = clip((TP − α · FALSE − β_v5 · UNKNOWN) / |G+|, −1, 1)，α = 1，β_v5 = 0.1，|G+| 是本图认证正事实的条数；
    原始断言超过 24 条时 R_v5 = −1。
  - 没有 perception 段、或 perception 段不止一个时，R_v4 = R_v5 = 0，R_format 也是 0。所以对 `rl_v5` 来说，写一段 R_v5 < −0.5 的
    perception（λ · R_v5 < −0.05）比不写更差；格式奖励 0.05 抵消的正是这部分。这是 S1 定下的权重（D7）的直接结果，试跑和训练中的格式率会显示它的影响。
  - 几何证伪只开点存在性、圆存在性、点在线上（归一化距离 0.06）、平行与垂直（容差 15°）、点在圆上（相对半径偏差 0.15）；
    角度大小、线段等长、角相等的几何检验关闭。一致性门控开启：标注否定了自身认证事实的图，同类检验不参与证伪（D35）。
  - λ 的取法（D7）：两种感知奖励的“λ × 取值范围”相同，0.2 × [0, 1] 与 0.1 × [−1, 1]。
- **安慰剂**：认证正事实、负事实和几何取自固定错位配对的另一行（种子 20261109，两行图像像素哈希不同），答案奖励仍用本题的标准答案
  （D8、D15）。每条 rollout 另记按本题元数据计算的 `v5_own`（D16）。
- **记号**：第 7 节的 KL 系数记作 β_KL = 0.01，与 v5 的 β_v5 = 0.1 无关。

## 7. 损失函数

TRL 1.17.1 的 `GRPOTrainer`，`loss_type = dapo`，`scale_rewards = batch`，`multi_objective_aggregation = sum_then_normalize`（TRL 默认）。
下面是这组设置下代码实际计算的量（核对的是 `trl/trainer/grpo_trainer.py` 1.17.1 的源码）。

**优势**。一步的 64 条补全按题分成 8 组，每组 8 条：

Â_i = (R_i − mean_{j ∈ 组(i)} R_j) / (std_{j ∈ 本步 64 条} R_j + 10⁻⁴)

std 是样本标准差（除以 n − 1）。分子按题居中，分母是整批的标准差：同一步里每道题用同一个尺度，三个奖励项的相对权重（λ 的含义）
不会被逐题的缩放改变（执行计划第 3 节第 3 条）。可选组 `rl_v5_groupnorm` 的分母改为本题 8 条的样本标准差。

**逐 token 目标**。对补全 i 的第 t 个 token：

ℓ_{i,t} = −min(ρ_{i,t} · Â_i, clip(ρ_{i,t}, 1 − 0.2, 1 + 0.28) · Â_i) · w_{i,t} + β_KL · ρ_{i,t} · k3_{i,t}

- ρ_{i,t} = π_θ / π_old，是同一 token 在当前参数与生成时参数下的概率比。每批只做一次更新，微批之间参数不变，ρ 只差两次前向的数值误差，
  接近 1，裁剪基本不起作用；ε = 0.2 / 0.28 与 DAPO 的设置一致。
- w_{i,t} = min(exp(log π_old − log π_vLLM), 2.0)：vLLM 采样与训练前向之间的 token 级截断重要性权重（`token_truncate`，上限 2.0，无下限，D41）。
- k3_{i,t} = exp(log π_ref − log π_θ) − (log π_ref − log π_θ) − 1。参考策略 π_ref 是关掉 LoRA 的 V0（TRL 对 PEFT 模型不另建参考模型）；
  β_KL = 0.01；TRL 默认的 `use_bias_correction_kl` 再乘 ρ。

**汇总**（DAPO 的 token 级平均）：L = Σ_{i,t} m_{i,t} · ℓ_{i,t} / Σ_{i,t} m_{i,t}，两个求和都覆盖本步全部 64 条补全；m 是补全 token 的掩码，
写到上限的补全整条为 0。梯度在 8 个微批上累积，然后做一次梯度裁剪（范数 1.0）和一次 AdamW 更新。每个微批的损失已经按整步的 token 数归一，
TRL 把它标记为 `loss_is_scaled_for_ga = True`，transformers 5.19 不会再除以累积步数，所以累积后的梯度正好是 ∇L。

## 8. 预算、checkpoint 与终止判据

**正常结束**：每个任务恰好做 228 次参数更新，然后停止。不提前停止，也不按任何指标挑选 checkpoint。每 38 步保存一次完整 checkpoint
（第 38、76、114、152、190、228 步）；训练结束后 `final/` 保存第 228 步的 LoRA adapter 和处理器；S5 只评测 `final/`。

**中断与失败**：

| 情况 | 处理 |
|---|---|
| 与训练计算无关的中断：VM 被回收、连接断开、`colab exec` 到达 24 小时上限、Drive 暂时不可用 | 从最近一个已核对的 checkpoint 恢复（第 12 节），运行身份必须完全一致；次数不限，每次都记录 |
| 训练计算本身失败：显存不足，某一步的 loss 或梯度范数为 NaN 或 inf，对齐检查、网格检查报错，奖励代码异常 | 任务停止。允许一次重启，从最近一个已核对的 checkpoint 恢复；再次失败就记为“失败”，不再重试。要改代码或运行时，先追加决策，并对所有组同时生效；已完成的任务如果受影响就重跑 |
| 登记检查不通过（第 9 节） | 不开始训练。查明原因，必要时追加决策并重新生成登记表 |

训练入口在每一步的日志里检查 `loss` 与 `grad_norm`，出现 NaN 或 inf 就立即停止。HF Trainer 在同一步里先写日志、再保存 checkpoint，
所以出问题的那一步不会写 checkpoint，也不会写 `final/`；`log_history.json` 照常写出，保留出问题的那一步。为此关闭了 HF Trainer
把 NaN loss 替换成平均值的日志过滤（`logging_nan_inf_filter`，只影响日志，D55）。

**任何时候都不做**：

- 根据奖励、准确率、格式率、长度、KL 或熵的走势重跑、丢弃或替换任务；
- 用别的种子替换失败的种子；
- 在任务进行中改配置、运行时或代码（恢复时运行身份必须一致，代码变了恢复会被拒绝）。

失败的任务在报告中列出；S5 用实际完成的任务分析，某组少一个种子时按完成的种子平均（S3 设计第 5 节）。

## 10. 运行顺序、批次与提前收尾

按登记表的 `order`，以种子优先的固定顺序开始任务：

| 顺序 | 任务 |
|---|---|
| 1–5 | 种子 1：`rl_v5`、`rl_ans`、`rl_blind`、`rl_v4`、`rl_v5_placebo` |
| 6–10 | 种子 2：同样五组、同样顺序 |

- 理由：任何时候停下来，已完成的任务在各组之间都尽量均衡。组内按参与主比较的项数排序：`rl_v5` 8 项，`rl_ans` 5 项，`rl_blind` 与
  `rl_v4` 各 2 项（`rl_blind` 同时参与 E2 和 E3，排在前面），`rl_v5_placebo` 1 项。

  可以同时用两台同型号的 A100 VM，各自按顺序取下一个还没开始的任务。顺序只决定开始的先后，不决定任务能否进入分析。
- 可选组只在 12 个正式任务都结束后才开始，是否运行不看任何正式任务的训练指标；它不进入 9 项主比较，只作探索。
- 提前收尾：Colab 余额低于 150 CU 时，或 2026-11-29 00:00 UTC 之后，不再开始新任务；已经开始的任务照常跑完。

## 12. Checkpoint 的 Google Drive 持久化与恢复

这一节由下一个 PR 的 `pilot` 与 `train` 任务实现；本 PR 只登记目录、标记文件名和保留规则（登记表的 `checkpoints` 段）。

- 训练只读写 VM 本地盘。每个 checkpoint 写完后，用 `rclone copy` 复制到
  `mydrive:ColabProjects/vlm-perception-reward-rl/s4/rl_v3_p1_20261110/<组>/seed<k>/checkpoint-<步>/`，再用 `rclone check --one-way` 核对大小和哈希，
  通过后才写 `DRIVE_VERIFIED.json`。不经 FUSE 挂载写入（D31）。
- 任务结束后，`final/`、`run_identity.json`、`train_summary.json`、`log_history.json` 和 `rollouts.jsonl` 同样复制到这个目录并核对。
- Drive 上每个任务保留最近一个已核对的完整 checkpoint 和 `final/`；新的 checkpoint 核对通过后，才删除运行器自己写入的上一个
  （估计每个完整 checkpoint 约 0.36 GB：adapter 约 0.12 GB，AdamW 状态约 0.24 GB；全部保留时 14 个任务约 30 GB）。VM 本地盘保留全部 checkpoint。
- 恢复只用带 `DRIVE_VERIFIED.json` 的 checkpoint：取回到原输出目录 `runs/rl_v3_p1_20261110/<组>/seed<k>/`，以 `--resume` 启动；
  运行身份（配置、包版本、源码、数据、运行时、提示长度、LoRA 目标）必须与 checkpoint 中的完全相同。
- 恢复后的任务与不中断的任务在统计上等价，但不逐位相同：HF Trainer 恢复了 Python、NumPy 和 torch 的随机状态，也跳过已经用过的题目；
  vLLM 引擎重建后采样随机流从头开始（引擎种子固定为 0，第 5 节）。恢复次数记录在任务结果里。
- 每个任务的小体积结果（摘要、日志、压缩后的 `rollouts.jsonl`）照常推到 GitHub 的 `results/<run_id>` 分支；权重和 checkpoint 不进 GitHub（D24、D37）。
