## 二、CF-Geo 是怎么做出来的

1. 规则只在 train 上开发。设计原稿的擦除方法（整框填背景色，框外一圈不均匀就排除）只保留了 14% 的 train 候选：
   数字常常紧挨线条，或者带单位（“3 cm”“4 in.”）。改成按连通块只擦数字本身、允许单位后，train 上保留 68%。
   这个改动作为 S3 设计的修订 1，提交并推送到 GitHub（`fe99e2e`）之后，才第一次对 validation 与 test 运行（D47）。
2. 第一次运行保留 159 题。第一轮抽查 30 题，没有发现数字错、位置错、擦除残留或线条被改；但有两个要全局修正的问题：
   k=1 把 “3.0” 重画成了 “3”（k=1 不再是原样重画）；原图数字较粗时，重画的数字明显更细。
3. 按抽查规则全局修正（编辑器 v3：k=1 原样重画印刷的字符串；在 4 倍分辨率下用描边加粗，使重画的原字符串与原数字的墨迹总量一致），
   全部重建，保留 158 题。第二轮从其余题中再抽 30 题，全部可用。记录在
   [spot_check.md](../../reports/cfgeo_20261109/spot_check.md)。
4. 用脚本核对全部 158 题：k=1 的字符串都与印刷的相同；k=1 和 k=2 都能由补丁重建出记录的像素哈希。

数据纪律（D44）：这一步读取了 validation 公开题和 test 的题面、答案与图像，用于构造评测集；抽查时我看了其中 60 题的原图和编辑图。
没有在任何留出题上运行模型。

按 158 题估计，E2 能区分的差异约 8–9 个百分点（S3 设计第 5 节的检验力估计按约 180 题算，结论不变）。

## 四、另外发现的问题

1. **S2 验收报告第三节第 1 条的一个推断不严格**（D50）。那里用 token 数推断“没有训练图会被 vLLM 或训练处理器缩小”。
   但处理器先把宽高按 28 取整，像素略少于 802,816 的图取整后可能超过上限而被缩小，例如 1024×783 会变成 1008×756。
   现在不靠推断：每次用 vLLM 训练前，逐张检查训练图在两种设置下的 patch 网格，不同就停止；结果写进 `train_summary.json`。
   公开 validation 与 test 的图都不会被缩小（沙箱里用同样的取整规则检查过）。
2. **数据包里的 InterGPS 标注是 CRLF 换行**（原文件在 Windows 上生成）。内容与用固定版本 InterGPS 压缩包重建的结果相同：
   把重建结果写成 CRLF 后，SHA256 与 `migration_manifest.json` 记录的 `d83517c4…` 完全一致。所以 VM 上用数据包里的标注重建评测集定义，
   与沙箱里的生成是同一份输入（D49）。读取代码按行解析，不受换行符影响。
3. transformers 5.19 对 `AutoProcessor.from_pretrained(..., max_pixels=..., min_pixels=...)` 给出弃用警告（5.23 起移除）。
   版本已固定为 5.19，训练和评测用同样的调用，没有影响；以后升级 transformers 时要改。
