## 1. 项目全貌与核心使命

本项目旨在研究：**视觉语言模型（VLM）在几何问题求解中是否真正使用了图像信息，还是仅仅依赖题面文本与语言先验进行“无图幻觉答题”？** 以及：**使用原图认证但排除题面已知信息的可证伪稀疏感知事实，能否通过 GRPO 强化学习提供可靠的训练信号，促进真正的视觉事实感知与几何推理？**

* **主模型**：`Qwen/Qwen2.5-VL-3B-Instruct`（固定 revision `66285546d2b821cf421d4f5eb2576359d3770cd3`）。
* **训练路线**：**所有正式组均直接从 V0（原始基座）出发**，只挂载针对语言部分的 LoRA（29,933,568 可训练参数），ViT 视觉编码器与 Merger 绝对冻结；**不做感知 SFT，也不做格式预热**（旧入口 `scripts.training.train_project3` 仅保留历史溯源，正式实验统一使用 `scripts.training.train_rl`）。
* **硬件环境**：Google Colab A100-SXM4-40GB（单卡），本地 WSL2 自动化调度，持久化依赖 Google Drive（挂载路径 `/content/drive/MyDrive/p3_colab_run`）。
* **核心输出协议 (P1)**：
  `<perception>事实; ...</perception><think>推理</think><answer>最终答案</answer>`

## 3. 实验矩阵与严密因果对照设计 (S4 预注册)

为从根本上排除“语言能力提高误作视觉理解”、“任意密集/格式奖励引入伪规律”等混淆，S4 设定了 5 大核心组别（种子 1、2、3）：

| 组别 (Arm) | 感知奖励类型 | 权重 $\lambda$ | 训练时图像 | 感知元数据匹配 | 核心对照职责 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **`rl_ans`** | 无 (0) | 0.0 | 是 | 本题 | **主对照**：仅靠答案奖励与格式奖励，测试纯 RL 解题极限。 |
| **`rl_v5`** | **v5.1 可证伪感知奖励** | **0.1** | 是 | 本题 | **主方法**：加入稀疏认证几何事实匹配与证伪惩罚。 |
| **`rl_v4`** | v4 (原稀疏 F1) | 0.2 | 是 | 本题 | **消融对照**：对比原有 F1 式感知奖励与最新 v5.1 的差异。 |
| **`rl_v5_placebo`** | v5.1 | 0.1 | 是 | **错位元数据**（模型看本题真图，感知奖励用固定错位配对题目的 gold/求解器判分） | **安慰剂对照**：如果错位元数据奖励也能带来提升，说明提升可能只来自“输出结构化断言”，而非看懂了本题图形。注意它不是中性对照：如实描述本题图形可能被错位求解器判为 FALSE，因此 `rl_v5 > rl_v5_placebo` 只说明奖励需要与本图对应，要结合 `v5_own` 与 blind/swap 条件判断视觉使用（S4 预注册修订 3）。 |
| **`rl_blind`** | 无 (0) | 0.0 | **否 (黑盒文本)** | 无 | **盲视对照**：完全无图训练，检验题面语言先验的基线天花板。 |
| `rl_v5_groupnorm` *(可选)* | v5.1 (组内标准化) | 0.1 | 是 | 本题 | **算法探索**：检验 GRPO 内部是否需要对感知奖励做组内标准化。 |

### 奖励函数定义
$$R = 1.0 \cdot R_{\text{answer}} + 0.05 \cdot R_{\text{format}} + \lambda \cdot R_{\text{perception}}$$
* $R_{\text{answer}} \in \{0, 1\}$：使用 SymPy / math_verify 常驻进程池严格判定模型提取的 `\boxed{}` 或 `<answer>` 内容。
* $R_{\text{format}} \in \{0, 1\}$：严格三段结构 `<perception>`、`<think>`、`<answer>`，且 `<perception>` 必须包含有效几何命题（条数 $\in [1, 24]$）。
* $R_{\text{perception}}$ (v5.1)：
  $$R_{v5} = \operatorname{clip}\left(\frac{TP - \alpha \cdot FALSE - \beta \cdot UNKNOWN}{|G^+|}, -1, 1\right),\quad \alpha = 1.0,\ \beta = 0.1$$
  见 `src/rewards/perception_v5.py`：TP 命中已认证事实，FALSE 被几何求解器（点存在、关联、平行/垂直、圆）或已认证常量证伪，
  其余为 UNKNOWN；超过 24 条为 −1；没有可信 gold 时 mask=False。一致性门控：本图自己的某条认证事实被求解器反驳时，
  该理由族的 FALSE 降级为 UNKNOWN。值域是 [−1, 1]，可以为负。
  （旧版 v4 才是 F1 式：$|P\cap pos| / (|P\cap pos| + |pos\setminus P| + 2|P\cap neg|)$，只用于 `rl_v4`。）

## 4. 数据边界与防泄漏铁律

* **批准数据量**：609 条训练事实（458 幅图）/ 82 条验证事实（77 幅图）。**这是部分认证事实（Partial Facts），绝非全图金标（Gold Standard）**。未标注的事实视为“未知（Masked）”，不可宣称能做全图精确召回或杜绝所有幻觉。
* **输入输出白名单严格隔离**：
  * **模型前向输入（White-list）**：严格仅包含 `problem` 文本与 `image_path`。
  * **私有标签（Private to Rewards）**：`reference_answer`、正例事实、负例事实、审核员评语由环境持有，绝不进入模型上下文。
* **数据目录结构与便携性**：
  * 本包完整收录 `data/portable_release/`（包含完整 `manifest.json` 与清洗后的 609+82 题 JSONL 数据）。
  * 本包收录了与核准题目前 20 题精准对应的真实几何图像（保存在 `data/topup_v6_20261024/project3/images/` 及 `data_samples/`），确保任何局部推理、提示构建、输入核对均可开箱即跑。

## 5. 期望外部 Agent 重点审查的核心议题

请审查专家直接对以下 5 个关键问题提出犀利批评或改进方案（请按优先级、受影响代码位置、最小复现或验证方式给出）：

### 议题一：感知奖励函数设计的作弊风险与尺度失衡
* **现状**：总奖励 $R = 1.0 \cdot R_{\text{answer}} + 0.05 \cdot R_{\text{format}} + 0.1 \cdot R_{\text{perception}}$。
* **疑点**：
  1. $R_{\text{answer}}$ 是极其稀疏的（S3 诊断在 64 题上 V0 准确率仅 4.3%），而 $R_{\text{perception}}$ 在 P1 提示下相对容易拿到部分分数（0.1 ~ 0.5）。模型是否会快速学会“拼命迎合感知格式与常见几何模式”，而放弃艰难的答案推理？
  2. 现有实现是否有防止模型“猜角度/猜长度罗列攻击”（Listing Attack）的绝对屏障？
  3. 代码位置：`src/rewards/`、`src/training/train_rl.py`。

### 议题二：因果假说与反事实评测的有效性
* **现状**：我们设计了 `rl_v5_placebo`（真图 + 错位元数据判分）与 `rl_blind`（无图），并在 S3 规划了 CF-Geo 几何反事实扰动测试。
* **疑点**：
  1. 几何题往往带有极强的文本泄露（例如题目问“在等腰三角形 ABC 中，AB=AC=5，BC=6，求面积”，文本其实已经把关键事实说完了）。这 609 道题中到底有多大比例是**必须依赖图像**才能解出的？
  2. 当前的数据集划分是否足以支持“视觉被真正使用”的科学主张？

### 议题三：GRPO 训练工程与超参数稳定性
* **现状**：
  * 单卡 A100-40GB，TRL + vLLM Colocate（vLLM 显存占比 0.3，最大上下文 4096）。
  * 批次配置：每步 8 题 × 8 采样 = 64 补全，微批 8，梯度累积 8，学习率 1e-5，3 个 Epoch 共 228 步。
  * 仅更新语言 LoRA（29.9M 参数），ViT 冻结。
* **疑点**：
  1. 在 3B-VL 模型上，GRPO 采样 8 条对于几何推理这种长链路任务，方差是否过大导致 advantage 估计失真？
  2. 是否需要将组内奖励标准化（`rl_v5_groupnorm`）提升为主方案？

### 议题四：Colab A100 抢占式调度与断线恢复
* **现状**：通过 WSL2 `colab/launch.sh` 脚本驱动 Colab CLI，利用 Google Drive 的原子锁与 state.json 进行任务断点接续与超时看门狗保护。
* **疑点**：
  1. Drive 挂载在 Colab 中偶发 I/O 延迟或只读回退，当前锁实现与 checkpoint 保存逻辑是否存在死锁或损坏风险？
  2. 代码位置：`colab/launch.sh`、`colab/kernel_job.py`。

### 议题五：正式训练启动门槛（Go / No-Go 判据）
* **现状**：S4 Pilot 试跑设定了 4 个开跑门槛（G1~G4，见 `docs/plan/S4预注册_20261110.md`）。
* **请教**：
  1. 当前这套判据是否足够严密？有没有漏洞可能让一次“注定失败或发散”的实验误入正式训练，耗费宝贵的 GPU 配额？
